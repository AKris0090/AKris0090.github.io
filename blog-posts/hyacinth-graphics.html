Hyacinth's Graphics Features (In Prog.)

Overview

This article will go over a few of the graphics features I implemented for Hyacinth's PBR renderer. Hyacinth takes a lot of influence from bits and pieces of Overwatch's rendering backend, all deciphered from publicly available articles and videos, which will be linked throughout the article (and below).

Notice: Many parts of this article will be speculation. I don't work on Overwatch (yet 🙏🙏🙏).

You can view the source code for my engine at: https://github.com/AKris0090/Hyacinth

Questing for Global Illumination

One of the more recent features that the Overwatch team has been public about in regards to their graphics is their shift to a baked DDGI system for global illumination. Previously, the game would rely on baked lightmaps to illuminate static world geometry, as described by Bruce Wilkie, in this article. The intensive lighting calculations for the world are performed ahead of time, stored in maps, and shipped out with the game. This saves a ton of computing resources on the client's side, and you get beautifully lit worlds with a simple texture lookup. Dynamic objects used a volume of prebaked lighting probes (foreshadowing).

Miniboss: Early Lightmapping

One of my earlier experiments in shadow mapping involved baking lightmaps for the world. Lightmapping involves using secondary texture coordinate for each world object, and assigning it a space in a texture. I used a library called xatlas to generate these UVs. I would then write the mesh information to a text file in an OBJ-adjacent file format. To bake lighting information, I would load the object from this custom file, generate acceleration structures on the device, and raytrace from each texel on the lightmap image into the world.

And while I was able to get lightmaps integrated into the renderer, the results left something to be desired. Handling the balance of light seams, texture resolution, filtering, and texel density proved to be a little bit above my grade at the time. I was able to achieve far more visually appealing results with run-time cascaded shadow mapping.

During a youtube scroll session, I came across this presentation by Will Pearce on the Overwatch team detailing the new baked DDGI system implemented for stadium maps. The core of this presentation focused around how they worked around the various memory and computational restrictions that exist to keep Overwatch running smoothly regardless of the platform.

The other part of this presentation covered the technical approach they used to give artists the freedom to place global illumination volumes around the scene, and control the amount of detail per volume. After doing some research into the RTXGI Github Repo and reading Chapter 14 of Mastering Graphics Programming in Vulkan, I dove headfirst into implementation.

Implementing DDGI

My implementation regards DDGI volumes as a portion of 3D space that consists of evenly distributed probes, represented as 3-dimensional points.

Irradiance probes.

Two volumes in this scene.

Each volume applies global illumination to the objects contained within them, which is determined by two textures that get baked before runtime. The irradiance texture stores the incoming diffuse lighting at each probe, and the visibility texture stores two moments of the hit distance from the probe to the closest geometry surface.

Irradiance Texture. RGB represents incoming diffuse light.

Visibility Texture. R and G represent mean distance and distance^2.

Each DDGI volume goes through a set of passes for the baking process. The first step in this process is raytracing from the probes in all directions to determine the incoming irradiance from all directions. For each probe, we trace a high number of rays in an even distribution around the unit sphere, described by a spherical fibonacci pattern. In shader, I calculate the diffuse lighting at each ray bounce and write the accumulated result to a giant arrayed image (width = # of rays, height = # of probes in plane, layers = # of planes in volume). For each pixel, the diffuse is stored in the r, g, and b, channels, while the alpha channel stores the hit distance from the probe to the nearest surface in that direction.

Multi-layered ray data image. Cropped version.

The second pass of this process runs a compositing process on the ray data image, and generates the irradiance and visiblity atlas (shown above) using a compute shader. Within each atlas, an island represents a single probe's octahedral map of diffuse/visibility data averaged over the direction each pixel represents. The last thing we need to do is fill in borders for the atlas to allow for proper bilinear filtering. You can find more information about the border pattern at this blog.

Finally, the evaluation pass samples from the 8 probes surrounding the world space position of the pixel in the image. For each of the 8 nearest probes, the distance and direction to the world space point are calculated and used to determine a trilinear weight. The two depth moments stored in the visibility texture are used to firstly determine if the distance to the point is greater than the average distance (there is likely an occluder), and if so, calculate the probability that the distance exists through Chebyshev's Inequality. The irradiance atlas gets sampled and added up. The final irradiance value is determined by averaging the total irradiance over the accumulated weights from the 8 probes.

One helpful aspect of this solution is that, unlike baked lightmaps, dynamic objects can receive global illumination by sampling from the volumes directly.

Stencil Optimization

How does this relate to Overwatch? In the presentation, Mr. Pearce goes over how they made use of stencil buffers to evalute DDGI for the scene starting with the smallest volume up to the largest, as compared to drawing the largest volume first and overlaying the smaller ones. This reduces overdraw by ensuring that the expensive DDGI evaluation gets perfomred only once per pixel.

This stenciling is made possible with two bits: a "current" bit and an "any" bit, describing the pixels the current volume is writing to, and pixels where any volume has written to previously. The first pass draws a volume to the stencil buffer, and tests againt the "any" bit. For each pixel, the world position is multiplied by the inverse transform of the volume, making it possible to determine if the point is contained within the bounds of the volume. If not, that pixel gets discarded in the fragment shader. All pixels that pass this depth discard test get the "current" bit set. 

m_volumeStencilPipeline.m_depthStencil.front.compareMask = ANY_BIT;
m_volumeStencilPipeline.m_depthStencil.front.writeMask = CURRENT_BIT;
m_volumeStencilPipeline.m_depthStencil.front.compareOp = VK_COMPARE_OP_EQUAL;
m_volumeStencilPipeline.m_depthStencil.front.reference = 1;
m_volumeStencilPipeline.m_depthStencil.front.passOp = VK_STENCIL_OP_REPLACE;
m_volumeStencilPipeline.m_depthStencil.front.failOp = VK_STENCIL_OP_KEEP;

At the time of GI evaluation, each pixel gets tested against this "current" bit. If the "current" bit is set, then it is known that the "any" bit is not set, so we invert both during the stencil test, ensuring that the "any" bit is set for the next stencil volume pass. 

m_ddgiPipelineUtil.m_depthStencil.front.compareMask = CURRENT_BIT;
m_ddgiPipelineUtil.m_depthStencil.front.writeMask = ANY_BIT | CURRENT_BIT;
m_ddgiPipelineUtil.m_depthStencil.front.compareOp = VK_COMPARE_OP_EQUAL;
m_ddgiPipelineUtil.m_depthStencil.front.reference = 1;
m_ddgiPipelineUtil.m_depthStencil.front.passOp = VK_STENCIL_OP_INVERT;
m_ddgiPipelineUtil.m_depthStencil.front.failOp = VK_STENCIL_OP_ZERO;

BONUS: Stencil Mapping for Outlines

After I got my hands dirty with stencil bufferring in the DDGI implementation, I looked towards applying my newfound knowledge towards outlining enemy characters. This application was a bit more advanced, as I wanted it to be a screen space effect AND I wanted to make sure I don't see outlines behind other objects.

// Stencil out the characters using a dedicated stencil bit and write the pixel depth to a separate depth texture // In compute shader, expand only the values with the stencil bit set, and use the depth sample from the previously rendered depth texture to compare with the full depth texture // After expanding the stencil, overlay the expanded texture onto the swapchain image by flipping the stencil mask, and rejecting pixels where the stencil bit is set.
